## 1. Corrections to the draft

**C1. The versioning row is incomplete, and the newest guidance is missing.** VERIFIED at
https://google.aip.dev/184, https://google.aip.dev/185#interface-based-versioning and
https://google.aip.dev/181#interface-based-stability-levels.
- AIP-184 "API version identifiers" was approved and created on 2026-08-17. The same commit (#1643, "IBV AIP updates") also:
  - added "Interface-based versioning" to AIP-185;
  - added interface-based stability levels (Experimental, Preview, General availability) to AIP-181;
  - added glossary terms (API variant, API interface version, API service version, API version identifier) to AIP-9.
- The draft maps versioning to 180/181/185 only. Add 184 and 205 (Beta-blocking changes), and note 182 is in Reviewing.

**C2. ML `:predict` is not covered by any AIP.**
- **Evidence:** zero matches for "predict", "inference" or "model serving" across all 73 live general pages. AIP-100 only mentions ML as an example of a team that may keep its own guidelines.
- **What the AIP does cover:** AIP-136 is still the correct rule source for the method shape. See
  its "Resource-based custom methods" and "Stateless methods" sections:
  https://google.aip.dev/136#stateless-methods.
- **Where `:predict` actually comes from:** Google precedent.
  - Vertex AI's `projects.locations.endpoints.predict` is `POST /v1/{endpoint}:predict` with `body: "*"`.
  - The old Vertex reference URL now 301s to https://docs.cloud.google.com/gemini-enterprise-agent-platform/reference/rest/v1/projects.locations.endpoints/predict (page last updated 2026-05-07).
  - Proto: https://github.com/googleapis/googleapis/blob/master/google/cloud/aiplatform/v1/prediction_service.proto.
- **The precedent itself deviates from AIP-136.** The resource field is named `endpoint`, but AIP-136 says the resource-name parameter **must** be called `name`.
- **Rule for the skill:** cite AIP-136 for the rule and cite Vertex only as precedent. Never copy its field naming as compliant.

**C3. The Design Guide changelog is not an AIP change feed.** VERIFIED at https://docs.cloud.google.com/apis/design/changelog.
- It logs only the guide's own changes. Newest entries: 2025-06 (Naming Convention redirected to an AIP) and 2024-10 (pages redirected to AIPs). It has nothing on the 2025–2026 AIP changes.
- Per-AIP Changelog sections are also incomplete:
  - AIP-181, 185, 190, 214, 142 and 202 have no Changelog heading at all.
  - AIP-203's June 2026 rule changes (etag exemption, oneof exemption, AIP-149 note) are not logged.
  - AIP-185/181's 2026-08-17 IBV additions are not logged.
- The authoritative change feed is the GitHub history (see §4).

**C4. "Most chapters point to AIPs" is understated. Every former chapter now 301-redirects to an AIP.** VERIFIED with curl.
- The following paths under `docs.cloud.google.com/apis/design/` all return 301:
  - `resources`→121, `resource_names`→122, `standard_methods`→130, `custom_methods`→136
  - `standard_fields`→148, `errors`→193, `design_patterns`→/general#design-patterns, `documentation`→192
  - `naming_convention`→190, `versioning`→185, `compatibility`→180
  - `file_structure`→191#file-layout, `glossary`→9, `proto3`→191#syntax
- Only three pages remain on docs.cloud.google.com:
  - the Introduction, which has its own intro and conventions text but whose "Sections" are pointers to AIPs;
  - Directory structure, which carries its own content;
  - Changelog.
- All three show "Last updated 2026-10-07".
- Fetching the guide intro on every task adds almost nothing; the AIP index is the real index.
- The draft's directory_structure URL is correct:

**C5. The licensing sentence is incomplete.** VERIFIED in the page footers, at https://google.aip.dev/licensing, and in the repo `LICENSE.md`.
- Text is CC BY 4.0 "except as otherwise noted". **Code samples are Apache 2.0.**
- Google trademarks and brand features are excluded, and embedded images, audio, video and linked decks are not covered unless noted.
- A bare References list does not match what Google's licensing page asks for. The "Modified
  versions" notice says portions are modifications of work shared by Google, names the CC BY 4.0
  license with a link, and links back to the source page.
- CC BY 4.0 §3(a) also requires indicating modifications. See §4.7 for wording.

**C6. The OpenAPI linting advice is risky as written.** VERIFIED.
- No Google-official AIP OpenAPI ruleset exists:
  - google.aip.dev never mentions OpenAPI except the FAQ, which says non-proto users should follow the "spirit" of the guidance: https://google.aip.dev/faq.
  - linter.aip.dev only lints protocol buffers.
  - Google Cloud API hub's built-in Spectral linter defaults to Spectral's generic OpenAPI rules, not AIP rules: https://docs.cloud.google.com/apigee/docs/apihub/validate-spec.
- The closest ruleset is AEP's Spectral ruleset, and it encodes AEP conventions that **conflict with AIPs** (see §5). Running it unmodified will flag correct Google-style designs.

**C7. Requirement-keyword typesetting.** VERIFIED at https://google.aip.dev/8#requirement-keywords.
- AIPs use only must, must not, should, should not and may, per RFC 2119, **lowercase and bold**. On the live HTML they appear as `<strong>must</strong>`.
- The Design Guide intro uses UPPERCASE bold and the larger RFC 2119 set (REQUIRED, SHALL, RECOMMENDED, OPTIONAL).
- AIP-8 also says:
  - Rationale sections **must not** contain guidance and must not use RFC 2119 terms, so never cite a requirement from Rationale or History.
  - should/should not **must** come with examples of valid overrides.
- **Caveat:** bold is not perfectly applied. AIP-164's new Expunge bullets use unbolded "must" (repo
  lines 119–121; https://google.aip.dev/164#expunge). AIP-200's "should also include an explanation"
  is unbolded. Report such text as "unbolded 'must' (likely intended as a requirement)" rather than
  silently upgrading or downgrading it.

**C8. Anchors exist but are not stable.** VERIFIED.

  - `#localizedmessage` moved from Rationale to Guidance.

## 3. Stale-prior traps

Each item gives the question to verify, then the current answer with its AIP link and requirement level. All are VERIFIED on live pages.

1. **Is API versioning only `v1`/`v1beta` channels?** No. Two AIPs now cover it, and they are in tension:
   - [AIP-185](https://google.aip.dev/185#interface-based-versioning) lists four strategies:
     channel-based (still "recommended"), **interface-based (new 2026-08-17)**, release-based and
     visibility-based.
   - Under IBV, [AIP-184](https://google.aip.dev/184) says:
     - identifiers **must** match `[VARIANT-]YYYY-MM-DD[-DECORATOR]`;
     - they **must** be sent via `X-Goog-Api-Version` header or `$apiVersion` query param, not both;
     - GA **must not** use a decorator, and preview is `YYYY-MM-DD-preview`.
   - On a missing identifier, AIP-184 says the request **must** fail with 400. AIP-185 says it
     **may** default to a producer-chosen version or consumer override, and **must** reject only if
     no default exists. Cite both and flag the tension.
2. **Can a read-only custom method use POST?** Yes, since 2026-06-09 ([AIP-136](https://google.aip.dev/136)):
   - the HTTP method **must** be GET or POST;
   - GET **must** be used for retrieval;
   - POST **may** be used for retrieval when the payload could exceed URL limits.
3. **Can soft-deleted resources be purged on demand?** Yes. [AIP-164 #expunge](https://google.aip.dev/164#expunge) was added 2026-04-28:
   - an `Expunge` custom method **may** be provided;
   - it is `POST …:expunge`, body `"*"`, returning Empty or an LRO;
   - it works on CREATING, READY or soft-deleted resources;
   - a separate expunge permission (e.g. `<service>.<resource>.expunge`) **must** be required.
4. **Is `field_behavior` optional?** No ([AIP-203](https://google.aip.dev/203#guidance)):
   - it **must** be on every field of request messages and sub-messages;
   - each field **must** use at least one of REQUIRED, OPTIONAL or OUTPUT_ONLY.
   - Since June 2026 (unlogged): a resource's `etag` **should not** have one, and oneof fields **may** omit it.
   - `IDENTIFIER` **must** be on `name`.
5. **Is `Status` + code + message enough for errors?** No ([AIP-193](https://google.aip.dev/193), approved 2024-11-04 after a 2024 rewrite):
   - every error **must** include `ErrorInfo`;
   - each detail type appears at most once (**must**);
   - dynamic message parts **must** be in `ErrorInfo.metadata`;
   - `Status.message` **should** be English. The changelog's 2023 "native language" line is superseded by the current body; git shows that text was removed in 2024-09.
6. **Must PERMISSION_DENIED or NOT_FOUND come first?** Permission **must** be checked before
   existence. No access returns 403 PERMISSION_DENIED (**must**); with access but missing returns
   404 NOT_FOUND (**must**). See [AIP-193
   #permission-denied](https://google.aip.dev/193#permission-denied).
7. **Is `update_mask` required?** No ([AIP-134](https://google.aip.dev/134), mask optionality made a must 2024-03-14):
   - the mask **must** be optional, and an omitted mask means all populated fields (**must**);
   - `*` (full replace) **must** be supported;
   - PUT **may** only be used for full-replacement-only methods and is strongly discouraged.
8. **Must batch mutations be atomic?** Not always
   ([AIP-233](https://google.aip.dev/233#atomic-vs-partial-success),
   [234](https://google.aip.dev/234), [235](https://google.aip.dev/235), changed 2025-03-06):
   - batch methods **may** be atomic or partial-success;
   - synchronous batch **must** be atomic;
   - async batch **may** be partial.
9. **May user-specified IDs look like UUIDs?** Yes. The prohibition was dropped 2025-03-10
   ([AIP-122](https://google.aip.dev/122)). IDs **should** follow RFC-1034 lowercase
   `^[a-z]([a-z0-9-]{0,61}[a-z0-9])?$`.
10. **Is `{resource}_id` on Create optional?** It depends on the plane ([AIP-133](https://google.aip.dev/133); planes are defined in [AIP-111](https://google.aip.dev/111)):
    - **must** for management-plane resources;
    - **should** for data plane.
11. **Should Get take a `read_mask` request field?** No. A read mask as a request field is **DEPRECATED** for Google APIs ([AIP-157](https://google.aip.dev/157#read-masks-as-a-request-field), 2025):
    - the system-parameter side channel **must** be used;
    - masks **should not** be in the request message.
12. **Is `uri` always preferred over `url`?** No, since 2025-09-15 ([AIP-140](https://google.aip.dev/140#uris)):
    - arbitrary URIs **should** use `uri`, and URL-only fields **should** use `url`;
    - well-known abbreviations (config, id, info, spec, stats) and unit abbreviations (`distance_km`) **should** be used;
    - field names **must not** be verbs.
13. **Is there a general naming AIP?** Yes: [AIP-190](https://google.aip.dev/190) (created 2025-06-10) replaced the guide's naming page.
    - Definitions **must** be UpperCamelCase unless otherwise specified.
    - Method names **should** be VerbNoun.
14. **Custom-method naming:** [AIP-136](https://google.aip.dev/136):
    - no prepositions (**must not**);
    - no "Async" (**must not**; a `LongRunning` suffix **may** be used);
    - verb **should not** be a standard-method verb;
    - URI uses `:verb` matching the RPC verb (**must**), in camelCase (**must**).
15. **Delete a parent that has children without `force`?** [AIP-135](https://google.aip.dev/135) (2024-06-11):
    - it **must** fail with FAILED_PRECONDITION;
    - if the only children are singletons, deletion **must** be allowed;
    - with a `force` field set false or unset and children present, it also **must** fail with FAILED_PRECONDITION.
16. **What does an etag mismatch return?** ABORTED (HTTP 409), not FAILED_PRECONDITION ([AIP-154](https://google.aip.dev/154), changed 2021; AIP-135 aligned 2022).
17. **How do partial List failures surface?** Through a repeated string `unreachable` field
    (**must**) holding service-relative names (**must**)
    ([AIP-217](https://google.aip.dev/217#pagination)). Pagination guidance changed on 2024-07-26
    (commit #1392 is marked breaking); those names **must** be included regardless of `order_by`.
18. **Where do LRO failures go?** [AIP-151 #errors](https://google.aip.dev/151#errors), 2025-02:
    - a failure to start **must** be a normal error response;
    - execution failures **must** be in `Operation.error`;
    - validate-only on an LRO method has a prescribed response (2024-04).
19. **How should `request_id` be typed?** [AIP-155](https://google.aip.dev/155):
    - it **should** be optional;
    - UUIDs **must** be annotated `(google.api.field_info).format = UUID4` ([AIP-202](https://google.aip.dev/202));
    - client libraries may auto-populate it ([AIP-4235](https://google.aip.dev/client-libraries/4235)).
20. **Are protobuf Editions acceptable?** No. Protobuf APIs **must** use proto3 syntax ([AIP-191 #syntax](https://google.aip.dev/191#syntax)); the page does not mention Editions.

Also note [AIP-180](https://google.aip.dev/180), 2025-10-21:
- raising a string's maximum length **should** be treated as incompatible;
- changing a field's value format or construction **must not** happen within a version;
- default values **must not** change.

### 4.10 REST/JSON translation facts (check 9). VERIFIED

- **Field casing:**
  - [AIP-140 #case](https://google.aip.dev/140#case): proto fields **must** be `lower_snake_case` and are mapped to an appropriate convention in JSON. AIP-140 does not itself say "camelCase".
  - [AIP-127](https://google.aip.dev/127): request bodies are encoded per protobuf's canonical JSON.
    Query params are camelCase, e.g. `?bookId=foo`. `json_name` **should not** be used except for
    backwards compatibility.
  - ProtoJSON maps keys to lowerCamelCase and parsers accept both forms:
    https://protobuf.dev/programming-guides/json/. AIP-127's own link,
    developers.google.com/protocol-buffers/docs/proto3#json, now 301s to
    protobuf.dev/programming-guides/proto3/.
- **ProtoJSON value forms** relevant to OpenAPI schemas:
  - int64/uint64 → decimal **string**;
  - Timestamp → RFC 3339 string;
  - Duration → `"1.5s"`;
  - FieldMask → comma-separated camelCase paths;
  - enum → name string;
  - bytes → base64.
- **HTTP mapping** ([AIP-127](https://google.aip.dev/127)):
  - every RPC **must** have an HTTP definition, except bidi streaming;
  - verbs are get/post/patch/delete, and put/custom **should not** be used;
  - GET and DELETE **must not** have a body;
  - the body **must not** be repeated or nested.

| Method | HTTP verb | Body |
|---|---|---|
| Get | **must** be GET | none (**must not**) |
| List | **must** be GET | omitted (**must**) |
| Create | **must** be POST; the collection **should** map to the URI path | resource field (**must**); `{resource}_id` as query param |
| Update | **should** be PATCH; `{resource}.name` **should** be the only path variable | resource (**must**); `update_mask` |
| Delete | **must** be DELETE | none (**must not**) |
| Custom | **must** be GET or POST, path `…/{name=…}:verb` | `"*"` **should**, but GET custom methods take no body (AIP-127) |

- **Error JSON** ([AIP-193
  #http11json-representation](https://google.aip.dev/193#http11json-representation)):
  `{"error":{"code":<HTTP status>,"message":…,"status":"<google.rpc.Code name>","details":[…]}}`.
  The `code` is the HTTP status, not the RPC code.
- **Major versions** ([AIP-185](https://google.aip.dev/185)):
  - **must** be in the URI path, e.g. `/v1/`;
  - **must not** expose minor or patch versions;
  - alpha/beta suffixes **must** be appended in channel-based versioning.

## 5. AEP recommendation (check 9). Facts VERIFIED

**What AEP is.**
- https://aep.dev is a **fork of aip.dev founded in 2023** by contributors who wanted a formal, organization-agnostic spec plus tooling (https://aep.dev/blog/history-of-aeps/, 2025-02-03).
- **Governance** is independent of Google ([AEP-6](https://aep.dev/6/)): a steering committee of at
  least 5 representatives from at least 5 organizations, with at most 1/3 from any one organization.
  The source of truth is the `aep-dev` GitHub repos.
- **Name inconsistency:** the site `<title>` now reads "Application Enhancement Proposals", while AEP-1, AEP-6 and the aep-2026 post say "API Enhancement Proposal(s)".
- **Editions:** `aep-2026` was released 2025-12-08, with a 2-year cadence (AEP-300). Tooling is promised compatible with the 3 most recent editions.

**HTTP/OpenAPI coverage and tooling.**
- AEP is explicitly HTTP/OpenAPI-first. Pages show HTTP examples and OAS terms, and AEP-134 covers JSON merge-patch over HTTP.
- **AEP OpenAPI linter exists:** https://github.com/aep-dev/aep-openapi-linter.
  - It is a Spectral ruleset (MIT), published on npm as `@aep_dev/aep-openapi-linter` 0.5.3 (2026-02-26).
  - Use it via `extends: ['@aep_dev/aep-openapi-linter']`.
- Other tooling: a proto linter fork, aepc, aepcli, a Terraform provider, an MCP server, and https://aep.dev/llms.txt.

**Divergences from Google AIPs.** VERIFIED on aep.dev and in the ruleset; each would mis-lint a Google-style API.

| Topic | AEP | Google AIP |
|---|---|---|
| JSON field names | **lower_snake_case** (AEP-140) | lowerCamelCase via ProtoJSON (AIP-127) |
| Resource identifier field | **`path`** (AEP-122; rule `aep-122-resource-path-field`) | `name` (AIP-122) |
| Page size | **`max_page_size`** (AEP-158) | `page_size` (AIP-158) |
| Update | rule `aep-134-content-type` expects **`application/merge-patch+json`** | `FieldMask update_mask` (AIP-134) |
| Delete response | **204 No Content** (AEP-135) | `google.protobuf.Empty`, or the resource for soft delete |
| URL fields | rule `aep-140-uri-property-naming` flags any `*url` property | AIP-140 (2025-09) prefers `url` for URL-only fields |
| Create ID parameter | `id` parameter (rule `aep-133-id-parameter`) | `{resource}_id` (AIP-133) |

**Recommendation.**
- Mention AEP at most once, as a **secondary aid for OpenAPI mechanics only**, for example how to express `:verb` custom paths, LRO polling or list schemas in OAS.
- **Never cite AEP to justify a design, and never let it override an AIP.** When they differ, the AIP wins and the agent says so.
- **Do not run `aep-openapi-linter` unmodified on Google-style APIs.** Either:
  - use only Spectral's generic `spectral:oas` ruleset (what API hub uses) and check AIP conformance by review against the fetched AIPs; or
  - extend the AEP ruleset with the conflicting rules turned off. At minimum:
    `aep-122-resource-path-field`, `aep-158-max-page-size-parameter`, `aep-134-content-type`,
    `aep-135-response-204`, `aep-140-uri-property-naming`, `aep-133-id-parameter`, plus any
    snake_case rules.
- The primary OpenAPI path stays: model in proto terms, then translate with AIP-127 and the ProtoJSON rules (§4.10).
